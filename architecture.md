# Платежный сервис — Архитектура
Принимает платежи и обрабатывает их через эмулируемый платёжный шлюз, отправляя Webhook для уведомления пользователя.

## Модель данных

### Payment - платежи
```
Fields:
id (UUID) — ID платежа
amount (NUMERIC(12,2)) — сумма платежа
currency (ENUM) — валюта платежа
description (TEXT) — назначение платежа
extra_data (JSONB | NULL) — дополнительные данные по платежу, в схеме поле возвращается как metadata
status (ENUM) — статус платежа
idempotency_key (VARCHAR UNIQUE) — ключ идемпотентности для гарантии единого платежа
webhook_url (TEXT) — url для вебхука
webhook_attempts (INT) — кол-во попыток отправки вебхука
webhook_last_error (TEXT) — текст последней ошибки при отправке веб-хука
webhook_delivered_at (TIMESTAMPTZ) — дата и время доставленного вебхука
created_at (TIMESTAMPTZ) — дата и время создания платежа
processed_at (TIMESTAMPTZ | NULL) — дата и время обработки платежа
```

### OutboxMessage - сообщения в брокер для обработчика
```
Fields:
id (UUID) — ID сообщения
payload (JSONB) — данные сообщения
event_type (ENUM) — тип события, обозначающий в какую очередь relay направит сообщение
status (ENUM) — статус сообщения (pending, sent)
retry_count (INT) — кол-во повторов отправки
last_error (TEXT) — текст последней ошибки
next_retry_at (TIMESTAMPTZ) — дата и время следующего повтора
sent_at (TIMESTAMPTZ) — дата и время отправки
created_at (TIMESTAMPTZ) — дата и время создания сообщения

Indexes:
INDEX (status, next_retry_at) — для эффективного поиска неотправленных сообщения в relay outbox паттерна
```

## Границы транзакций
Транзакции четыре, все короткие. Всё долгое вынесено между ними.
1. Создание платежа (API). INSERT платежа и INSERT записи в outbox, затем COMMIT. Обе вставки в одной транзакции — в этом и весь смысл outbox. Если ловим IntegrityError по idempotency_key, откатываем транзакцию целиком и отдельным запросом читаем уже существующий платёж, его и возвращаем.
2. Цикл relay. SELECT ... FOR UPDATE SKIP LOCKED батчем, публикация каждой записи в RabbitMQ, UPDATE статуса и sent_at, COMMIT. Публикация происходит внутри транзакции — это осознанно. Если процесс упадёт после publish, но до commit, запись останется pending и уедет ещё раз. Повторная доставка безопасна, потому что консьюмер идемпотентен, а вот потеря события — нет.
3. Консьюмер, чтение. Короткий SELECT платежа. Если статус уже не pending — делаем ack и выходим, шлюз не дёргаем.
4. Консьюмер, запись результата. UPDATE ... WHERE id = :id AND status = 'pending' RETURNING id, затем COMMIT. Если RETURNING пустой — платёж уже обработал кто-то другой, выходим без webhook'а.

Плюс короткая транзакция после доставки webhook'а: пишем webhook_attempts, webhook_delivered_at или webhook_last_error.

Вне транзакций остаются два вызова: обращение к шлюзу (2–5 секунд) и отправка webhook'а (до 10 секунд на попытку, попыток три). Держать транзакцию открытой на время внешнего запроса нельзя — соединение из пула занято, строка заблокирована, а чужой сервер может отвечать сколько угодно или не ответить вовсе.

## Гарантии
**Идемпотентность API.**
От чего защищает: клиент дважды нажал кнопку или повторил запрос после таймаута. Держится на UNIQUE(idempotency_key). Проверку «а есть ли уже такой» заранее не делаем: при одновременных запросах оба SELECT вернут пусто, потому что READ COMMITTED не показывает чужие незакоммиченные вставки. Поэтому сразу INSERT, а на нарушении уникальности откатываемся и отдаём тот платёж, который успел создаться первым.

**Идемпотентность консьюмера.**
От чего защищает: сообщение доставлено дважды (штатная ситуация при at-least-once) или процесс умер между COMMIT и ack. Держится на UPDATE ... WHERE status = 'pending' — строка обновится только у одного консьюмера, второй получит пустой RETURNING, сделает ack и выйдет. Webhook отправляет только выигравший, так что клиент не получит два уведомления об одном платеже.

**Outbox.**
От чего защищает: платёж записан в базу, а событие в брокер не ушло — упал процесс, недоступен RabbitMQ. Атомарности между PostgreSQL и RabbitMQ не существует, поэтому событие пишется в ту же базу и той же транзакцией, а доставкой занимается отдельный процесс. Упал relay — запись осталась pending и уедет на следующем цикле. Гарантия получается at-least-once, дубли снимает предыдущий пункт.

**Retry и DLQ.**
От чего защищает: платёж не удалось обработать — база была недоступна, шлюз вернул ошибку. Сообщение уходит в retry-очередь и через TTL возвращается в основную. Счётчик попыток берём из заголовка x-death, который проставляет сам RabbitMQ, — поэтому он переживает рестарт консьюмера, в отличие от счётчика в памяти процесса. На третьей неудаче отправляем сообщение в payments.dlq.

## Схема очередей
Один direct exchange и три очереди.
* payments.new — основная, на неё подписан консьюмер. Relay публикует сюда, routing key определяется значением event_type.
* payments.retry — с x-message-ttl = 5000 и dead-letter-exchange обратно на payments.new. Сообщение просто лежит пять секунд.
* payments.dlq — конечная точка, отсюда ничего не возвращается.

## Сознательные ограничения в рамках тестового
Тело запроса при повторном Idempotency-Key не сравнивается. Если клиент пришлёт тот же ключ с другой суммой, он получит первый платёж. Правильнее хранить хеш тела и отдавать 409 при несовпадении — не стал делать, потому что ТЗ этого не требует.

Нет ручки для повторной отправки недоставленных webhook'ов. Данные для неё есть — webhook_attempts, webhook_delivered_at, webhook_last_error. Добавить можно за полчаса, но в рамках задания это выходит за рамки.

Retry-очередь одна, TTL фиксированный. Экспоненциальная задержка потребовала бы трёх очередей с разными TTL — механика ровно та же, объём больше.

Outbox-таблица не чистится. Отправленные записи копятся. В проде на это вешается периодическое удаление старше N дней, sent_at для этого и нужен.

failed в OutboxStatus нет намеренно — публикация ретраится бесконечно с backoff, терминального состояния у записи не возникает
